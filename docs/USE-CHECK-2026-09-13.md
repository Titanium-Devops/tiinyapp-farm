# Can a stranger use tiinyapp.farm? A run through it, 2026-09-13

Everything below was **measured**, not reasoned about. One machine: Jason's MacBook Pro
(Mac17,6), macOS 26.6.2 (Darwin 25.6.0), Python 3.14.6, home broadband in Central Texas,
2026-09-13 between 22:05 and 22:15 UTC. The site was the live one at https://tiinyapp.farm
and the CLI came from the real PyPI, not from this checkout, except where a row says
"patched source".

Nothing in this document is a plan. The plans are in the owned rows at the end, and they
are labelled as such.

that gap is row **O-8** below. `/Users/sem/tiinyapps` did not exist before the run and does
not exist after it, and `/Users/sem/.tiinyapps` still holds only the `token` file it held

That last row settles a question worth being explicit about, because the first two rows look
alarming and are not. The 403 is cross-site request protection on the browser form path. A
bearer token skips it, so the exact `curl` that `docs/agents.txt` prints for an assistant
reaches the authentication layer and fails only on the token. The documented agent path is
sound. A syntactically valid but fake token was used to establish the ordering of the gates;
no account was created and no real credential was used.

The Cloudflare block on the Python standard library, which was the largest finding of the
launch pass, **is gone**. Seven pages including `/` and `/docs/agents/` answer 200 to the
default `Python-urllib` user agent, and the project's own sweep is green in both columns.
`docs/LAUNCH.md` still told an operator to go fix it, so this branch corrects that document.

## What would stop a stranger, worst first

1. **O-1. `farm start <id> --port N` cannot move TiinyBench, and the error message
   recommends exactly that.** `farm/farm.py` moves an app off its declared port by rewriting
   the command line for `titanium-tiiny-bot` and by setting `PORT` for `story-lantern`, both
   matched by app id. Every other app gets `TIINYAPP_PORT` and nothing more. TiinyBench never
   reads it: its `--serve` flag takes the port, defaulting to 8425, and the string
   `TIINYAPP_PORT` does not appear anywhere in its release. So `--port 7832` is silently a
   no-op. Worse, when 8425 is busy the CLI says `Port 8425 is already in use; use farm start
   tiiny-bench --port N.`, and following that advice fails the same way. Two apps out of four
   need a line of CLI code each to be movable, which means the next community app will not be
   movable either.
2. **O-2. A refused port printed a Python traceback from a previous run.** The port check
   raised through the helper that quotes the last ten lines of `farm.log`. Nothing had been
   launched, so those lines were from an earlier attempt. A stranger saw a clear one-line
   message followed by an unrelated stack trace and could not tell which one to believe.
3. **O-3. Story Lantern dies without a device and nothing points at `farm device`.**
   `farm install story-lantern` succeeds, then `farm start` exits 1 with the app's own words,
   `Set TIINY_HOST and TIINY_KEY`. Those are environment variables the launcher sets from
   `~/.tiinyapps/device.json`, so the thing to do is run `farm device`, and no message said
   so. The CLI knows the manifest declares device models and knows whether that file exists.
4. **O-4. `farm status` printed five column headings over six columns.** The heading was
   `APP PID PORT UPTIME VERSION` and a row read `titanium-tiiny-bot 48122 7831 2s running
   0.1.13`. The last column is a status, sometimes with a note like `restart to update`
   after it, and calling it VERSION makes the row look misaligned.
5. **O-5. The install prompt showed raw JSON.** The line a stranger reads before agreeing to
   an install was `Needs: {"device": {"models": ["chat", "tts"], "npuUnits": 57}, "ports":
   [7788], "python": "3.11"}`. The spec says the site renders a manifest in plain words; the
   prompt that actually asks for consent did not.
6. **O-6. A mistyped app id littered the home directory for ever.** `farm start nope`,
   `farm stop nope` and `farm remove nope` each took the per-app lock before finding out the
   app was never installed, so each left a zero byte `~/tiinyapps/.locks/nope.lock` behind,
   and the first one created `~/tiinyapps` on a machine with nothing installed. Found the
   hard way: this run began with no `~/tiinyapps` on the machine and ended with a
   `.locks/nothing-here.lock` sitting in one, from a command run outside this check. Pure
   reads like `farm list` create nothing, so it is only the app-scoped commands.
7. **O-7. `docs/LAUNCH.md` sent the operator to fix something already fixed.** Step 4 and
   finding 9 described a Cloudflare rule refusing `Python-urllib`, with a table of 25 red
   fetches. Measured today, all 66 are green. Findings 4 and 5 were also resolved and still
   read as open.
8. **O-8. The CLI has no way to use a different home.** `Farm.__init__` accepts a `home`
   argument but `main()` never passes one and there is no environment variable, so `farm`
   always writes to `~/tiinyapps` and `~/.tiinyapps`. Testing it, or running two farms side
   by side, means overriding `HOME` for the whole process. Also, both paths collapse onto the
   same directory when `home` is given, so even the internal argument does not reproduce the
   real two-directory layout.
9. **O-9. `farm list` labels installed apps with their name and catalog apps with their
   pitch.** The same app reads `titanium-tiiny-bot 0.1.13 - Titanium Tiiny Bot` in one
   section and `- A local assistant with chat, files, memories and voice.` in the other.
10. **O-10. No app in the catalog has a screenshot.** All four pages end at "No screenshots
   yet", including the flagship, while the submit form asks makers for up to eight. Carried
   forward from the launch pass, still true.
11. **O-11. `SPEC.md` puts the device config in the wrong place.** It says
    `~/tiinyapps/device.json`; the code and the live install page both say
    `~/.tiinyapps/device.json`. The code is right.

Five of the six CLI changes were re-run against the live catalog with the patched source,
not only in tests: the prompt, the heading, the device hint, the clean port refusal and the
lock cleanup all behave as described on this machine. The sixth, the port diagnosis in O-1,
is covered by test only, for the reason below.

O-1 deserves a caveat about what the fix does and does not do. The CLI cannot make a third
party app read an environment variable. What it can do is stop the failure from being silent,
and it now names the cause and the remedy. Making `--port` actually work for every app needs
the manifest to say how the app takes a port, which was row **F-1** and is now the section
below.

The port diagnosis was proved by test rather than on the live box. Reproducing it for real
needs TiinyBench's declared port 8425 to be free, and on this machine an unrelated process
from Jason's own `tiiny-bench` checkout, started at 08:29 CDT, held it for the whole run. It
was left alone. With 8425 busy the app dies on the bind instead of hanging, which is the
other branch, and that branch already shows the bind error in the log tail.

## The manifest says how an app takes its port, measured 2026-09-13

Branch `port-field`, same machine as the run above: Jason's MacBook Pro (Mac17,6), macOS
26.6.2, Python 3.14.6, 2026-09-13. This closes **F-1** and **F-2**, and the two rows are gone
from the owned table below because they are no longer pending.

A manifest may now carry one optional field, `port`, that says how the app takes the port
`farm start` gives it: `{"argv": "--port"}` for a flag the number follows, `{"env": "PORT"}`
for an environment variable, or `null` for a port that is fixed. Leave it out and the farm
sets `TIINYAPP_PORT`, exactly as it always has, so nothing in the catalog changes meaning.
`farm start` reads the field and no longer knows any app by name.

**F-2 turned out not to need a TiinyBench release at all.** Its `--serve` already takes the
port: `bench.py` at tag v0.1.1 declares `--serve` with `nargs="?"`, `const=8425`,
`type=int`, `metavar="PORT"`. So the fix is one line of manifest, not a version bump, and
nothing was asked of the app's author. Read from the released tag on GitHub, not from a
local checkout.

What each manifest got, and why:

| App | Field | Why |
| --- | --- | --- |
| `titanium-tiiny-bot` | `{"argv": "--port"}` | `lite/server.py` parses `--port`, and the manifest entry already passes `--port 7788`. It reads no port environment variable, so the old `TIINY_PORT` the CLI used to set was never read by anything |

## What this run could not test

- **Anything that needs a Tiiny.** This machine has none. Every device call was either
  refused by the app or pointed at a placeholder base URL and key. Whether the four apps do
  useful work against real firmware, and specifically whether OneLane 0.1.0 and Story
  Lantern 0.1.0 fail on Tiiny 1.0 as the brief says, is untested here. That is still the one
  leg only an operator with hardware can walk.
- **Anything behind a sign-in.** No account was created, so email codes, GitHub sign-in,
  TiinyVerse profile verification, the submit form itself, media upload, `farm publish` with
  a real token, and the review pull request it opens were all read and never exercised.
- **The port-override diagnosis on the live box**, for the reason given above. Proved by
  test.
- **`farm update` actually installing a newer version.** All four apps are at their catalog
  version, so every update was the no-op path. The upgrade path, and whether data survives
  it, was not exercised.
- **Windows and Linux.** macOS only.
