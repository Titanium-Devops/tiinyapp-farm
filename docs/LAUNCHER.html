tiinyapp.farm Design document

The Tiiny App Farm Launcher

A signed desktop app for Mac and Windows that installs and runs farm apps for people who will never open a terminal. It carries its own Python and the farm command-line tool inside itself, so there is nothing to install first.

Design, 2026-09-13. Owner Jason Brashear. Nothing here is built. Every number names where it was measured or read, and estimates say so.

What it is

The launcher is a small signed desktop app for macOS and Windows that installs and runs farm apps for a person who will never open a terminal. It carries a standalone Python runtime and farm/farm.py inside itself and uses them as its engine, so there is nothing to install first: no Python, no Node, no Docker, no package manager. You download one file, open it, it finds your Tiiny on the network, you paste your key once, you pick an app from the same catalog the site shows, and half a minute later that app is running on your own computer with a menu bar or tray icon that says so. It is a face on the command-line tool that already exists, not a second way of doing things: same install directory, same device settings file, same lock, same logs. Somebody who starts with the launcher and later learns the CLI finds their apps exactly where the CLI expects them.

Who it is for

The person who bought a Tiiny AI Pocket Lab because it looked interesting, runs macOS or Windows, and would not get past step one of the current install page. That page opens with pip install tiinyapp-farm and a note about what to do when pip answers "externally managed environment". The note is correct, and it is also the moment a consumer closes the tab. Linux users are not the target: they already have the CLI and are the least likely to need this.

There is a second, smaller audience. A maker who wants somebody non-technical to try their app has to hand over a paragraph of terminal instructions today. With the launcher it is a link.

The first run, screen by screen

  1. DownloadThe install page shows one button that already knows the platform, with the other one underneath as a small link.
  2. Open itOn macOS, drag to Applications from a notarised and stapled disk image, with no Gatekeeper argument. On Windows, an installer that installs for the current user and never asks for an administrator.
  3. Find your TiinyThe launcher probes http://openai.api.tiiny/v1 first, which is what the TiinyOS client publishes on a Mac, then offers a box for http://<your-tiiny-ip>/v1. Both are the forms the site documents today.
  4. Paste the key onceThrough the same code path as farm device: ~/.tiinyapps/device.json at mode 0600, never echoed, never in a command line. Apps then receive the base URL, the key and the derived host from the launcher exactly as the CLI sets them.
  5. Pick an appA grid of the live catalog. Icon, name, one line, and the badges the site already computes: Reviewed, New, Library, No release yet. Opening a card shows what the app needs and what access it asks for before anything is downloaded.
  6. Plant itOne button, and progress for the three steps that are real: download, checksum, unpack. The checksum is the CLI's, and an archive whose checksum differs is never unpacked.
  7. It runsThe launcher waits for the app to be ready, up to the CLI's ten second ceiling, preferring the manifest health path when there is one. Then an Open button pointing at the app's own address on this machine.
  8. The trayA menu bar icon on Mac, a tray icon on Windows, listing what is running with Open, Stop and Update beside each. Closing the window does not stop anything.

Nothing in that list asks a person to understand a port, a virtual environment or a checksum, and nothing in it is new behaviour. Steps four through eight are the existing device, install, start, status, stop and update commands with a window in front of them.

Three shapes, and which one to build

A. A Tauri shell, a bundled Python, farm.py as the engine

A Rust and web-view app, the same stack as the Titanium Bot desktop app, carrying a standalone CPython tree and farm.py as bundled files. The shell draws the catalog and the tray; every action runs the bundled interpreter against the bundled CLI. One behaviour, two faces.

The reuse is not theoretical. The existing desktop app is Tauri 2 with the tray icon, notifications, the updater, single instance, autostart, the OS credential store, macOS hardened runtime with an entitlements file, and a Windows installer in current-user mode. Its two workflows already sign, notarise, staple and then verify the result before they will upload it.

One sharp edge, worth knowing before the first line of code. The Tauri bundler signs frameworks and sidecar binaries inside out and only those, so a Python tree copied in as a resource reaches the notary unsigned and is refused. The good news is the size of that job: a whole CPython 3.11.13 install for macOS arm64 holds four Mach-O files out of 2,762 files in total. Four signing calls in the workflow, before the app is signed, and the tree is legal.

Recommended.

B. An Electron shell, same engine

The same idea with a browser instead of a web view. The catalog interface could share code with the site, which is the honest argument for it, and more people can write it. It costs four to five times the download and throws away the signing pipeline, because Electron notarises through electron-builder rather than through the two workflows that are already green.

Held in reserve, and not the first fallback.

C. A native pair: SwiftUI on macOS, WinUI 3 on Windows

The best first-run feel and the smallest Mac download. Also two applications, two languages, two interface codebases and two sets of bugs, with the Windows half being the one that has the least existing work behind it. For a launcher whose whole job is a grid, a progress bar and a tray menu, that is a large bill for a small gain.

Declined on cost, not on quality.

Recommendation

Build shape A: Tauri, a bundled Python, farm.py as the engine.

Three reasons, in order. The release pipeline exists and is proven green on both platforms, so this is a user interface job and not a distribution project. The download stays in the range where a consumer does not think twice, and the gap against Electron is 100 MB of somebody's hotel wifi. And because the engine is the same file the CLI ships, there is one install format, one device file, one lock and one set of failure messages to support, forever.

Keep Electron on the shelf for exactly one contingency. If bundling a runtime inside a notarised app turns out to be worse than four signing calls, the fallback is not Electron. It is to fetch the runtime on first run, which is decision 2 below.

Signing, notarisation, and what Jason has to buy

Nothing new. Both certificates are already paid for and already wired into GitHub Actions.

macOS. Distributing outside the App Store needs a Developer ID Application certificate, notarisation and a stapled ticket. The Apple Developer Program is 99 USD a year, from Apple's own enrollment page read on 2026-09-13, and the membership is current: team F2DH8T4BVH, with a Developer ID Application certificate recorded in the signing notes as valid to 2027-02-01. The existing macOS workflow imports the certificate into a throwaway keychain, builds a universal binary, notarises through either the App Store Connect API key or an app-specific password, and staples the disk image itself, which the bundler does not do on its own. It also refuses to upload anything that macOS Gatekeeper and the stapler do not accept. Copy it as it stands and add the runtime signing step.

Windows. Azure Artifact Signing, formerly Trusted Signing, is 9.99 USD a month on the Basic plan for up to 5,000 signatures, from Microsoft's pricing page read on 2026-09-13. The account is live: the existing Windows workflow signs against the signing account Titanium and the certificate profile titanium-public, authenticating with a GitHub federated credential scoped to the main branch and no client secret anywhere. It then fails the run unless Windows itself reports the signature Valid. No hardware token, no dongle.

One honest caveat for the launch email. A correctly signed installer from a publisher with no download history can still show the SmartScreen "More info" panel until reputation accumulates. That is a function of downloads over time, and no certificate purchase removes it.

Two details in those workflows that were learned the hard way and must survive the copy. The bundle output directory is cleaned before every build, because the build cache otherwise carries an older installer into the artifact and into the signing step. And the build fails on its own if the updater private key does not match the public key in the config, because that mismatch is only a warning from the tool, which means a green build whose every update is silently refused by every installed app.

Auto update

The Tauri updater, the same one the desktop app uses: a signed tarball plus a small JSON feed at a fixed URL, the signature verified before anything is applied, and Windows installing in passive mode. The feed and the artifacts sit on the Cloudflare Worker that already serves the site, next to the R2 bucket that already holds submitted archives. The macOS workflow already writes that feed from the signature file rather than from anything retyped.

Two update tracks, kept apart in the interface because they are different questions. The launcher updates itself quietly on a restart. Apps update through the CLI's update command, which installs only a newer version and keeps the data directory, and the launcher shows a badge when the catalog version differs from the installed one. The status command already computes that comparison, including the case where a running app reports a different version than the one on disk.

What an app declares, and what the launcher can honestly provide

The manifest already carries the answer. requires holds an optional minimum Python version, the ports the app listens on, and the device block with model names and NPU units. entry is either a Python module with arguments or a command string.

The bundled runtime works for every app in the catalog today without touching a single manifest, because of one line in the CLI's start path: a command whose first word is python or python3 is rewritten to the interpreter the CLI is itself running under, which under the launcher is the bundled one. Story Lantern's python3 lantern.py and Tiiny Bench's python3 tiiny-bench --serve therefore run on the launcher's Python unchanged, and Titanium Tiiny Bot's module form was always going to. The floor to bundle is 3.11, because that is what Titanium Tiiny Bot requires; the other three ask for 3.9.

Free from the launcher

  • Its own CPython, 3.11 or newer, which is what the manifest's Python floor is measured against.
  • A writable data directory per app, handed over in the environment the CLI already sets.
  • SQLite, because it is in the Python standard library and a database is a file in that data directory. Nothing to install, no server to run.
  • The device base URL and key, the derived host, and the shared OneLane lock directory, so two apps take turns on one Tiiny instead of colliding.
  • A port check before start, and a working port override when something else already holds one.

Never from the launcher

Docker. MySQL, Postgres, or any database that is a server. Anything that needs an installer, an administrator prompt, a system service or a kernel extension. A compiler toolchain. If an app needs those, it is not a farm app, and the right place to say so is the submission check rather than a support email six months later.

A second runtime, if and only if a real app needs one

Node is the only plausible candidate. The proposal is a requires.runtime enum that defaults to Python, with the Node build fetched on demand into the launcher's own directory rather than shipped to everybody who never uses it. Do not add the field before the first app that needs it exists.

What the launcher does not do, stated plainly in the interface. It does not sandbox anything. Permissions in a manifest are declared by the author and shown to the person before installing. They are not enforced at runtime, which is what the CLI's own documentation says today. The launcher shows them on the card and in the confirmation, and claims nothing more.

What changes for makers

Almost nothing, deliberately. Same tar or tar.gz archive, same checksum and exact byte size in the manifest, same download and unpack ceilings, same refusal of symlinks, special files, traversal paths and duplicate entries, same static scan, same offline selfcheck, same cap on a publish upload. There is no launcher-specific package format and there never should be, because the moment there are two, an app works in one place and not the other.

Three small things do change, and all three are presentation:

  • An icon stops being optional in practice. The launcher's grid is icon first. Three of the four manifests today carry one; the submission flow should generate or require it rather than let a card ship blank.
  • A health path becomes strongly recommended. Without it the launcher can only say "started". With it the launcher can say "ready", and can tell a person when the running version no longer matches the installed one.
  • The requires block grows a runtime field only when a non-Python app appears.

Nothing in the review pipeline changes. A maker who never hears about the launcher keeps publishing the way they publish now, and their app appears in it.

What the site shows a consumer who has no CLI

  • On the install page: the download button becomes the top of the page, with the platform detected in a few lines of JavaScript and the other platform offered underneath. The three existing steps stay, moved below a heading along the lines of "Prefer the command line?". Nobody loses anything; the default path stops being the developer one.
  • On every app page: beside the copyable install command, a button that opens the app in the launcher through a deep link, falling back to the install page when nothing on the machine handles the scheme. The desktop app already registers two schemes this way, so it is configuration rather than new code.
  • On the home page: the hero's second button changes from "Install an app" to "Get the launcher".

All of it is static site work in the existing build script. No manifest changes, and no Worker changes except serving the download and the update feed.

Decisions for Jason

  1. Shape: Tauri, Electron, or a native pair

    Tauri reuses the signed pipeline and ships near 25 MB on Mac. Electron costs roughly 130 MB before our own code, and a new notarisation path. The native pair is two codebases for one grid.

    Recommended: Tauri

  2. Bundle the Python runtime, or fetch it on first run

    Bundling means one download and no network step, and puts four Mach-O files through the signing workflow. Fetching saves 16 to 48 MB in the installer and sidesteps the runtime signing question entirely, because a separately downloaded interpreter is a separate process and not part of our signature, at the cost of a first-run download and a checksum to verify.

    Recommended: bundle, with fetch held as the phase 0 fallback

  3. How the shell talks to the engine

    Add a JSON output mode to the CLI and run it as a child process, or embed the interpreter and import the Farm class in process. The child process with structured output is simpler, keeps the CLI honest, and makes the CLI better for AI agents at the same time. In process is faster and couples the two together.

    Recommended: a JSON mode on the CLI, about two days of the phase 1 budget

  4. Does the launcher also put the farm command on the PATH?

    Automatic means a consumer's shell gains a command they did not ask for. Never means a developer who starts with the launcher installs the same thing twice.

    Recommended: a one-click toggle in Settings, off by default

  5. Updater keypair

    A new keypair for the launcher, or reuse the desktop app's. Separate keys mean a compromise or a loss touches one product. A lost key strands every installed copy of whatever it signed.

    Recommended: a new keypair, in Bitwarden before phase 5

  6. Where the downloads and the feed live

    The farm's existing Cloudflare Worker and R2 bucket, or GitHub Releases. The Worker keeps one domain and one set of analytics and is already deployed. GitHub Releases is free bandwidth and a public download count.

    Recommended: the Worker, artifacts in R2

  7. Windows architectures

    x64 only, or x64 and arm64. Every architecture is another signed artifact and another build leg. Windows on ARM is a small but growing share of new consumer laptops.

    Recommended: x64 at launch, arm64 when somebody asks

  8. Name, bundle identifier and deep link scheme

    Decided once and painful to change, because the identifier is what the operating system uses to recognise an installed app across updates. Suggestion: the product name "Tiiny App Farm", the identifier farm.tiinyapp.launcher, the scheme tiinyfarm.

    Recommended: as suggested, unless the name is wrong

  9. Linux

    Ship an AppImage as well, or say no. The consumer premise is Mac and Windows, and Linux users already have a working pip install.

    Recommended: no, and say so on the download page rather than leaving people guessing

  10. Does the launcher sign in to a farm account?

    Browsing and installing need no account today; only publishing does. Adding sign-in means the account flows, the token store and a support surface, for a person who wants to run an app.

    Recommended: no sign-in in version 1; publishing stays in the CLI

What this costs

No new subscription. The Apple membership at 99 USD a year and the Azure signing plan at 9.99 USD a month are both paid and both already automated, the Cloudflare Worker and the R2 bucket already exist, and the runtime is free and redistributable. The cost of the launcher is two weeks of building it, and one more release artifact to sign per version after that.
